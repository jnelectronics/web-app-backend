## Architecture

**Flat structure, not the modular scaffold the README describes.** Everything lives at repo root: `main.py` (app + router wiring + exception handlers), `database.py` (engine/session/`Base`/mixins/`get_db`), `models.py` (all SQLAlchemy models), `schemas.py` (all Pydantic schemas), `security.py` (hashing, JWT, auth dependencies), `routers/<domain>.py` (one file per domain, routes only). Chosen deliberately over the original `app/modules/<domain>/{router,service,repository,schemas,models}.py` layered scaffold for being simpler to reason about at this project's size and while learning — revisit if it stops scaling.

**Shared model conventions** (`database.py`):
- `UUIDPrimaryKeyMixin` — every table's PK is a `uuid.UUID` named `id`, not an auto-increment int.
- `TimestampMixin` — every table gets `created_at`/`updated_at`, set by Postgres (`server_default`/`onupdate=func.now()`), not by Python.
- `get_db()` — the one `Session`-per-request dependency every router uses.

**Recurring gotchas already hit once — don't reintroduce them:**
- SQLAlchemy `Enum()` columns default to storing the Python enum member's *name* (`"ACTIVE"`), not its `.value` (`"active"`). Every enum column needs `values_callable=lambda e: [x.value for x in e]` to match the lowercase values the docs specify.
- Pydantic v2 `@property` on a response schema is invisible to JSON serialization — needs `@computed_field` above `@property` or the field silently disappears from the API response.
- This project doesn't use SQLAlchemy `relationship()` anywhere — only raw FK columns. Don't assign e.g. `order.items = [...]`, it does nothing; `db.flush()` for the parent's id, then explicitly `db.add()` each child row.
- Deleting rows manually across FK-linked tables (e.g. test cleanup) needs an explicit commit per table in dependency order — SQLAlchemy won't infer delete order across raw FKs. Also watch for tables that reference the SAME row from two different fixtures (e.g. a customer's cart *and* their orders) — clean up every referencing table before the row they point at, regardless of which fixture created what.
- A `Mapped[datetime]` column with no explicit `mapped_column(DateTime(timezone=True))` is created as a *naive* (timezone-unaware) column. Fine for purely informational timestamps, but if the column is ever compared against `datetime.now(timezone.utc)` in code (like `RefreshToken.expires_at`), that comparison raises `TypeError: can't compare offset-naive and offset-aware datetimes` — make any column you intend to compare explicitly timezone-aware.
- pytest fixtures finalize in **reverse** setup order (LIFO). If fixture B's teardown deletes rows that reference rows fixture A's teardown also deletes, order matters both ways — either fixture's teardown may need to defensively clean up the other's leftover references (see `tests/test_order_status.py`'s `staff_tokens` fixture for an example: it has to clear `order_status_history` rows itself because its teardown runs before `order_setup`'s).
- **`app.include_router()` call order in `main.py` matters** — Starlette matches routes in registration order, using the raw path template, *before* FastAPI validates any typed path parameter. A router registered with `GET /payments/{payment_id}` (where `payment_id: uuid.UUID`) will happily match a request for `GET /payments/webhook` first if it was registered earlier, treating `"webhook"` as the (not-yet-validated) `payment_id` — sending the request into the wrong handler entirely (this actually happened: PesaPal's webhook calls were landing in `read_payment`'s auth check and returning 403 instead of hitting `payment_webhook`). Any router with a fixed-path route that could collide with another router's `{param}` route must be registered first.
- **This dev machine tends to accumulate stale listeners on common ports** (8000, 8001, 8010 have all been seen occupied by leftover/unrelated processes from other projects) — and Windows will route a request to `localhost:<port>` to whichever process is bound to `127.0.0.1:<port>` specifically, even if a DIFFERENT, correct process is simultaneously bound to `0.0.0.0:<port>` on the same port. Symptom: the server you just started looks like it's running fine (clean startup log, no bind error) but every request returns something clearly wrong/stale/unrelated. Don't assume your own code broke - run `netstat -ano | grep :<port>` (or `Get-NetTCPConnection -LocalPort <port>` in PowerShell) and check the owning PID before debugging further. Easiest fix: just pick a different, verified-empty port for manual testing rather than fighting for a popular one.
- A custom Pydantic `field`/`AfterValidator` that raises a plain `ValueError` (e.g. `schemas.py`'s `PasswordStr`) makes Pydantic embed the actual `ValueError` **object** inside `exc.errors()`'s `ctx.error` field when FastAPI turns it into a `RequestValidationError`. `main.py`'s `validation_exception_handler` builds its own `JSONResponse` from a plain dict (for the custom error envelope), which does NOT run through FastAPI's encoder automatically the way returning a Pydantic model would - passing raw `exc.errors()` straight to `JSONResponse(content=...)` then crashes with `TypeError: Object of type ValueError is not JSON serializable`. Fixed by wrapping it in `fastapi.encoders.jsonable_encoder(exc.errors())` (the same helper FastAPI's own default handler uses internally for this exact reason). Caught by `tests/test_login_security.py`'s weak-password tests - worth remembering any time a new custom validator gets added anywhere in `schemas.py`.

**Established patterns to follow for new domains:**
- Soft delete (`is_active: bool`) instead of real row deletion — matches the docs, e.g. `routers/products.py`'s `DELETE` just flips the flag. Append-only audit-style tables (`RefreshToken`, `OrderStatusHistory`, `InventoryMovement`, `AuditLog`) skip `TimestampMixin` entirely and get only a manual `created_at` — they're never updated after being written, so there's no `updated_at` to track.
- Price/name fields the customer already saw get *snapshotted* onto the child row at the moment of the action (`CartItem.unit_price_snapshot`, `OrderItem.product_name_snapshot`/`unit_price`) so later edits to the source row don't retroactively change something already committed to.
- Domain-specific business-rule errors (e.g. `InsufficientInventoryError`, `DuplicatePaymentError`, `InvalidStateTransitionError`) are plain Python exception classes registered via `@app.exception_handler(...)` in `main.py`, not raised as raw `HTTPException` inline — keeps the HTTP-status/`error_code` mapping in one place.
- Every successful response is wrapped in `{"success": true, "message": ..., "data": ...}` automatically — give a router `route_class=EnvelopeRoute` (import from `envelope.py`) at construction and every route on it gets wrapped for free, no per-route changes needed. Errors get the matching `{"success": false, "message", "error_code"}` shape via the global exception handlers in `main.py` (`HTTPException`, `RequestValidationError`, and each domain-specific exception above all have one). A 204 response is left alone (no body to wrap).
- Auth: two separate identity tables/flows, not one. `Customer` (+ `get_current_customer` in `security.py`) for storefront users; `StaffUser` (+ `require_staff_role(*roles)`, a dependency *factory*, in `security.py`) for internal/admin users. JWTs carry a `type` claim (`"customer"` vs `"staff"`) so one token type can't be used where the other is required. There is no public staff self-registration — `POST /staff` requires an existing Inventory Manager/System Administrator, and creating a `system_administrator` through the API is always rejected; the first admin only ever comes from `seed_admin.py`. Refresh tokens (`RefreshToken` model) are random strings, hashed with fast SHA-256 (`security.hash_refresh_token`) — NOT Argon2 like passwords, since they're already high-entropy secrets, not guessable human input, and get checked on every `/auth/refresh` call. They are **not rotated** on use, only revoked (`/auth/logout` revokes every active one for the caller's account — there's no per-token targeting since the docs give `/auth/logout` no request body).
- Some endpoints accept *either* a customer or any staff role ("Owning Customer or Staff" in the docs) — there's no single dependency for this in `security.py`. Each router that needs it (`routers/payments.py`, `routers/orders.py`) defines its own local actor-resolution dependency that decodes the JWT's `type` claim and returns either a `Customer` or `StaffUser`. Small duplication, favored deliberately over a shared abstraction, matching this project's "auth logic specific to a domain lives in that domain's router" convention (see also `cart.py`'s `get_current_cart`).
- Role gating is **literal per-endpoint**, matching API spec §3.1/§3.3 exactly — System Administrator is NOT an implicit superset of Inventory Manager/Sales Attendant permissions (it's scoped to "seeded account, initial configuration only" per the docs). Don't assume admin can do something just because a manager can; check what the docs actually list for that specific endpoint. `routers/audit.py` is a good example of this cutting the other way — it allows System Administrator but NOT Sales Attendant, the opposite of most other staff-gated endpoints.
- Real external integrations: **Payments now use the real PesaPal API 3.0** (see the dedicated section below) — no longer simulated. Everything else still is: `POST /products/{id}/images` just stores a URL the client already has hosted, no real Cloudinary upload; `/auth/password/forgot` returns the reset token directly in the response *and* queues a (simulated, print-only) email job. Each has a comment at its point of use explaining the simplification.
- A router whose response format is dictated by an external caller (not our own API clients) should NOT use `route_class=EnvelopeRoute` — see `routers/payments.py`'s `webhook_router` vs `router`. Wrapping PesaPal's IPN acknowledgment in our own `{"success","message","data"}` envelope would break PesaPal's ability to parse it; it expects its own exact shape back.
- External-service calls (`pesapal_client.py`, `jobs.py`) get **mocked at the test-suite boundary**, not hit live on every `pytest` run — see `tests/test_payments.py`'s `mock_pesapal` fixture, which patches `routers.payments.submit_order_request`/`get_transaction_status` (patch where the name is *used*, i.e. already imported into `routers.payments`, not where it's *defined* in `pesapal_client.py` — patching the origin module doesn't affect a name some other module already imported directly). The real integration is verified once, separately, against actual sandbox credentials — not something the automated suite depends on.
- Business-rule write actions get logged to `audit_logs` via `audit.write_audit_log(db, ...)` — called *inside* the same transaction as the actual change (before `db.commit()`), never in its own commit, so the audit entry and the change it describes can't succeed/fail independently. Currently wired into product create/update/status, inventory adjust, staff create/update, and order status advancement — not yet every mutating endpoint (categories/branches/variants/banners/discounts/images aren't audited yet).

## Testing

Real `tests/` pytest suite (`tests/conftest.py` provides `client` — a `TestClient(app)` — and `db` — a direct `SessionLocal()` session for setup/teardown the API itself has no endpoint for). Runs against the live Neon DB, same as manual `/docs` testing always did — there's no separate test database. `conftest.unwrap(response)` pulls `response.json()["data"]` since every success response is now envelope-wrapped (see `EnvelopeRoute` above). One file per phase (`test_payments.py`, `test_role_gating.py`, `test_customers.py`, `test_auth_tokens.py`, `test_order_status.py`, `test_promotions.py`, `test_catalog_extensions.py`, `test_inventory_movements.py`, `test_dashboard.py`, `test_audit_logs.py`). Every test that creates rows must tear them down itself, in FK-safe order (see the gotcha above) — nothing here uses transactional rollback-per-test.

## How to work in this repo

This is a teaching context, not a normal "ship it" repo — the user is building this specifically to learn, and has given explicit, repeatedly-reinforced process rules:

- **Explain, don't just do.** Before writing a file/running a command, briefly say what it will do and why (the underlying concept, not just the mechanics). After, briefly explain what changed and why it matters. Keep explanations short and concrete — a couple of sentences, not an essay — but never skip the "why."
- **Gate on one file/command at a time.** Write or run exactly one coherent unit of work (one full file, or one full route/feature-sized addition, or one command) — then stop and let the user confirm before continuing. Don't chain multiple file writes or commands in a row without a checkpoint in between, even if the overall task was already agreed to.
- **Decide, don't ask.** For sequencing/pedagogy calls ("test this now vs. build the next file"), state the instructor's decision rather than presenting it as an open choice. Only ask real questions when it's a genuine product/scope decision only the user can make.
- **Comment code generously**, assuming a beginner-in-programming reader — explain what a decorator/mixin/dependency *is* and why a line exists, tutorial-style, not terse production-style. This is the one place in this codebase where the general "don't over-comment" default is intentionally inverted.

## Payments — PesaPal API 3.0 (real gateway, not simulated)

Client chose PesaPal over LivePay (LivePay had a 0/100 ScamAdviser trust score, hidden domain ownership, and IPQS phishing reports — too risky for a real payment integration; see project memory for the full comparison).

**Flow:** `POST /orders/{id}/payments` calls `pesapal_client.submit_order_request(...)`, stores PesaPal's real `order_tracking_id` as `Payment.provider_reference`, and returns a `redirect_url` — the frontend must send the customer's browser there (PesaPal's own hosted checkout page; we never build a card/mobile-money form ourselves). PesaPal's IPN then hits `GET /payments/webhook` with `OrderTrackingId`/`OrderMerchantReference`/`OrderNotificationType` query params — **deliberately without the actual payment status** (a PesaPal security measure) — so the handler calls `pesapal_client.get_transaction_status(...)` itself to find out what really happened, maps PesaPal's four statuses onto our `PaymentStatus` enum via `_map_pesapal_status` (`REVERSED` currently collapses onto `FAILED` — this project doesn't model refunds as their own state yet), and responds with PesaPal's required acknowledgment JSON (`{orderNotificationType, orderTrackingId, orderMerchantReference, status}`) — not our usual envelope, not the updated `Payment`.

**✅ Verified with a real, live, end-to-end sandbox test (2026-07-21)** — real checkout, real PesaPal hosted payment page, real IPN callback through an ngrok tunnel, real DB update. This is no longer just "should work in theory." One real bug was caught and fixed by that test — see below.

**`_map_pesapal_status` must compare case-insensitively.** The docs' examples show `payment_status_description` values in all-caps (`"COMPLETED"`), but PesaPal's real sandbox returned Title Case (`"Completed"`) in the live test — an exact-match comparison silently mapped a genuinely successful payment to `FAILED`. Fixed with `.upper()` before comparing; don't remove it, and don't trust the docs' exact casing for any new PesaPal status field without checking a real response. `tests/test_payments.py::test_map_pesapal_status_is_case_insensitive` pins this.

**Env vars needed** (`.env`): `PESAPAL_CONSUMER_KEY`, `PESAPAL_CONSUMER_SECRET`, `PESAPAL_BASE_URL` (sandbox `https://cybqa.pesapal.com/pesapalv3` vs live `https://pay.pesapal.com/v3` — **the base URL must match which kind of credentials you have, or auth fails with a confusing `invalid_consumer_key_or_secret_provided` error that looks like a bad key/secret but isn't**), `PESAPAL_IPN_ID` (from running `register_pesapal_ipn.py` once), `PESAPAL_CALLBACK_URL` (where the customer's *browser* lands after paying — a page on the real storefront frontend, not this API; defaults to a localhost placeholder that must be replaced before going anywhere near real users).

**Two distinct credential sets exist for this project, both currently in `.env` (commented differently) — don't mix them up:**
- **LIVE** — the client's real JN Electronics PesaPal merchant account (arrived by email). Currently commented out/inactive in `.env`. Settlement isn't set up yet (no signed contract with PesaPal) — do **not** activate these for anything except an intentional, careful, real-money test once the client confirms the contract is signed.
- **SANDBOX** — PesaPal's own **publicly published** shared demo/test merchant credentials (a `pesapal_sandbox_keys.json` PesaPal distributes, with one credential set per country — Kenya/Uganda/Tanzania/etc.). No signup needed, no real money, safe to commit to memory/docs (though still not to git). This project uses the **Ugandan Merchant** set (matches the target market) and is what's currently active in `.env` for all local dev/testing.

**Local dev needs a public tunnel** (`ngrok http <port>`) for `register_pesapal_ipn.py` and for PesaPal's IPN to actually reach this API — PesaPal is a real external service and cannot call `localhost`. ngrok's free tier now requires an account + authtoken (`ngrok config add-authtoken <token>`) even to start a tunnel. If ngrok errors with `ERR_NGROK_121` ("agent version too old"), run `ngrok update` first — the winget package installs an outdated version.

**PesaPal's access token expires every 5 minutes** — `pesapal_client.py` caches it in a module-level variable with a 30-second refresh margin rather than fetching a new one per call.

**Currently in "coming soon" mode for real users.** The client's LIVE PesaPal merchant account is pending PesaPal's business verification/settlement contract - so even though the integration is proven end-to-end against sandbox, `.env` intentionally runs on sandbox credentials, not live ones, for now. `pesapal_client.is_configured()` returns `False` only when NEITHER key is set (i.e. `initiate_payment` degrades gracefully if `.env` ever ends up with no PesaPal credentials at all - e.g. a fresh clone before setup); with the sandbox credentials in place, payments work for testing purposes. **Switching to real live payments is a deliberate `.env` edit (swap which credential block is active + change `PESAPAL_BASE_URL` to live) that should only happen once the contract is signed** - not an automatic "credentials exist so go live" flip.

**Known, deliberate simplifications** (each has an in-code comment at its point of use):
- No real external integrations anywhere (Cloudinary, payment gateway, email) — each is simulated in-process rather than stubbed as a fake client.
- Audit logging covers product/inventory/staff/order-status writes only, not categories/branches/variants/banners/discounts/images yet.
- Refresh tokens aren't rotated on use, only revoked.

**Background workers — built two ways; only one is currently wired in.**

**Currently ACTIVE: FastAPI `BackgroundTasks`.** `routers/auth.py`'s `forgot_password` calls `background_tasks.add_task(send_password_reset_email, ...)` (`jobs.py`) - runs in the same process as the API, after the response is sent, no separate worker or Redis needed. Chosen for the pilot launch specifically because **Render's Background Worker service type has no free tier at all (starts at $7/month)**, while the free Web Service plan was already sufficient. Trade-off, accepted deliberately: if the web process restarts mid-task, the task is lost - acceptable for a job this low-stakes (worst case, a user re-requests a password reset); revisit if a future job actually needs to survive a restart or genuinely can't run in-process.

**Built but NOT called from anywhere: RQ + Redis + a real worker process.** `redis_queue.py` (connection + the shared `job_queue`), `worker.py` (the standalone process: `python worker.py`, runs forever pulling jobs off Redis). This is a fully working, previously-verified-live alternative - switching back means changing exactly one call site (`background_tasks.add_task(...)` → `job_queue.enqueue(...)` in `routers/auth.py`), not rebuilding anything. Worth reviving if: job volume grows enough that blocking the request thread matters, a job needs to survive a process restart, or the project reaches a point where $7/month is trivial compared to what real cross-process queueing buys.

Redis for that path runs locally via Docker: `docker run -d --name jn-redis -p 6379:6379 --restart unless-stopped redis:7-alpine`, `REDIS_URL=redis://localhost:6379` in `.env`. `--restart unless-stopped` means it survives a Docker Desktop restart automatically. (A free Render Key Value instance was also confirmed available if this path gets revived in production - only the Background Worker service type itself is the paid piece.)

**Two genuine Windows/RQ incompatibilities were hit building the RQ path - both fixed, both worth knowing before reviving `worker.py`/`jobs.py`'s RQ call site:**
- RQ's regular `Worker` class forks a child process per job (`os.fork()`) for isolation - `os.fork()` doesn't exist on Windows at all and crashes the instant a job arrives. Fixed by using `SimpleWorker` instead (runs jobs in the same process, no fork). Trade-off: a job that crashes badly enough could in theory take the whole worker down with it, not just itself - acceptable for this project's jobs.
- RQ's default job-timeout mechanism (`death_penalty_class`) relies on `signal.SIGALRM`, also Unix-only. Fixed by overriding it to `rq.timeouts.TimerDeathPenalty` (a background-thread-based timeout that works cross-platform) - it's a class attribute, not a constructor argument, so it gets set on the worker instance after construction (`worker.death_penalty_class = TimerDeathPenalty`), not passed into `SimpleWorker(...)`.

`tests/test_background_jobs.py` tests the currently-active `BackgroundTasks` path - `TestClient` runs background tasks to completion before `client.post(...)` returns, so a plain assertion after the call works, no special waiting needed.

## Observability (Sentry + logging)

**Two separate PROCESSES need their own setup** — the API (`main.py`) and the worker (`worker.py`) never share a Python process, so configuring Sentry/logging only in `main.py` would leave the worker silently unmonitored. Both call `observability.setup_observability()` once at their own startup — see that file's docstring. Don't configure Sentry/logging directly in `main.py` or `worker.py` again; add to `observability.py` instead so both processes stay in sync.

**`enable_logs=True`** means Python's standard `logging` module output goes to Sentry too, not just unhandled exceptions — one dashboard for both instead of a separate logging service. Get a logger the normal way (`logger = logging.getLogger(__name__)`) and call `logger.info`/`.warning`/`.exception` — no per-file setup needed, `logging.basicConfig()` in `observability.py` already configured the root logger. Currently wired into `jobs.py` (replacing an old `print()`), `routers/orders.py`'s `checkout` (order placed / insufficient stock), and `routers/payments.py` (payment initiated, PesaPal gateway failures, webhook outcomes) — not yet every route. The two CLI scripts (`seed_admin.py`, `register_pesapal_ipn.py`) deliberately still use `print()`, not `logging` — they're one-off scripts a human runs and reads output from directly, not part of the running service.

**Log level is the signal for what becomes a Sentry Issue vs. a quiet breadcrumb.** `logger.info`/`.warning` for expected business outcomes (a declined card, insufficient stock, a stray webhook callback) — these matter for visibility but aren't bugs. `logger.exception`/`.error` for genuine infrastructure failures (PesaPal unreachable) — these SHOULD interrupt someone. Sentry's default behavior turns ERROR+ into its own Issue; INFO/WARNING become breadcrumbs attached to whatever error follows, not separate alerts. Keep using this distinction deliberately when adding new log calls — logging a normal business outcome at ERROR level would create alert fatigue.

**`send_default_pii=False`, overriding Sentry's own onboarding snippet default of `True`** — this project handles real customer PII (emails, phone numbers, delivery addresses); sending it to a third party needs to be a deliberate future decision, not the default.

**pytest runs now genuinely talk to real Sentry** (tagged `environment=development`, from `.env`) — there's no test-mode bypass. Test runs occasionally show `"Sentry is attempting to send N pending events"` in the output; that's expected, not a bug. If Sentry's dashboard ever needs to be read cleanly without test noise, filter by environment.

**Testing logger output needs `caplog`, not `capsys`.** `logging.basicConfig()` runs once at import time and binds its handler to whatever `stderr` existed then; pytest's `capsys` substitutes `sys.stdout`/`sys.stderr` per-test, which the already-bound handler doesn't see. `caplog` attaches its own handler directly to the `logging` module instead, independent of stream redirection — use it for any test asserting on log output (see `tests/test_background_jobs.py`).
