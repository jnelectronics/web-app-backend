# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FastAPI backend for the JN Electronics online shopping platform, built as a **learning project** — the user is a beginner in programming generally (not just FastAPI) and is building this to understand backend concepts, not just to get a working API. See "How to work in this repo" below before writing any code.

Full requirements/design docs live in `docs/` — `JN_API_Specification.md` and `JN_Database_Design_Document.md` are the ones actually referenced day to day (both Markdown; the `.pdf`/`.docx` siblings are the same content in other formats). Treat these as the source of truth for endpoint shapes, table columns, enums, and business rules — when unsure whether a field/rule is real or assumed, check the spec rather than guessing.

**`README.md` is stale.** It describes the original one-shot scaffold (`app/modules/<domain>/{router,service,repository,schemas,models}.py`, Docker Compose, `requirements/{base,dev,prod}.txt`) that was deleted and rebuilt from scratch (see Architecture below) — it hasn't been updated to match. Don't trust it for setup/run instructions; this file and the actual repo state are authoritative.

## Commands

```bash
# Run the API (reload on file changes)
uvicorn main:app --reload

# Create a migration after changing models.py, then apply it
alembic revision --autogenerate -m "description"
alembic upgrade head

# Seed the one System Administrator account (only way one can be created)
python seed_admin.py

# Run the background job worker (separate long-running process)
python worker.py

# Start Redis locally via Docker, if the container isn't already running
docker run -d --name jn-redis -p 6379:6379 --restart unless-stopped redis:7-alpine

# One-off: register this API's webhook with PesaPal (needs a PUBLIC url,
# e.g. via `ngrok http 8000` during local dev - PesaPal can't reach localhost)
python register_pesapal_ipn.py https://<public-url>/api/v1/payments/webhook
```

```bash
# Run the test suite (real DB, no mocks - see "Testing" below)
pytest tests/ -v
```

No Docker — runs directly against a hosted Neon Postgres instance via `DATABASE_URL` in `.env` (see `.env.example`). If a Neon branch goes stale (e.g. `password authentication failed` out of nowhere), check the Neon dashboard before assuming it's a code bug — the connection string may need updating in `.env`, and every migration will need `alembic upgrade head` re-run against a fresh/empty branch before new ones can be autogenerated.

## Architecture

**Flat structure, not the modular scaffold the README describes.** Everything lives at repo root: `main.py` (app + router wiring + exception handlers), `database.py` (engine/session/`Base`/mixins/`get_db`), `models.py` (all SQLAlchemy models), `schemas.py` (all Pydantic schemas), `security.py` (hashing, JWT, auth dependencies), `routers/<domain>.py` (one file per domain, routes only). Chosen deliberately over the original `app/modules/<domain>/{router,service,repository,schemas,models}.py` layered scaffold for being simpler to reason about at this project's size and while learning — revisit if it stops scaling.

**Shared model conventions** (`database.py`):
- `UUIDPrimaryKeyMixin` — every table's PK is a `uuid.UUID` named `id`, not an auto-increment int.
- `TimestampMixin` — every table gets `created_at`/`updated_at`, set by Postgres (`server_default`/`onupdate=func.now()`), not by Python.
- `get_db()` — the one `Session`-per-request dependency every router uses.

**Recurring gotchas already hit once — don't reintroduce them:**
- SQLAlchemy `Enum()` columns default to storing the Python enum member's *name* (`"ACTIVE"`), not its `.value` (`"active"`). Every enum column needs `values_callable=lambda e: [x.value for x in e]` to match the lowercase values the docs specify.
- Pydantic v2 `@property` on a response schema is invisible to JSON serialization — needs `@computed_field` above `@property` or the field silently disappears from the API response.
- This project doesn't use SQLAlchemy `relationship()` anywhere — only raw FK columns. Don't assign e.g. `order.items = [...]`, it does nothing; `db.flush()` for the parent's id, then explicitly `db.add()` each child row.
- Deleting rows manually across FK-linked tables (e.g. test cleanup) needs an explicit commit per table in dependency order — SQLAlchemy won't infer delete order across raw FKs. Also watch for tables that reference the SAME row from two different fixtures (e.g. a customer's cart *and* their orders) — clean up every referencing table before the row they point at, regardless of which fixture created what.
- A `Mapped[datetime]` column with no explicit `mapped_column(DateTime(timezone=True))` is created as a *naive* (timezone-unaware) column. Fine for purely informational timestamps, but if the column is ever compared against `datetime.now(timezone.utc)` in code (like `RefreshToken.expires_at`), that comparison raises `TypeError: can't compare offset-naive and offset-aware datetimes` — make any column you intend to compare explicitly timezone-aware.
- pytest fixtures finalize in **reverse** setup order (LIFO). If fixture B's teardown deletes rows that reference rows fixture A's teardown also deletes, order matters both ways — either fixture's teardown may need to defensively clean up the other's leftover references (see `tests/test_order_status.py`'s `staff_tokens` fixture for an example: it has to clear `order_status_history` rows itself because its teardown runs before `order_setup`'s).
- **`app.include_router()` call order in `main.py` matters** — Starlette matches routes in registration order, using the raw path template, *before* FastAPI validates any typed path parameter. A router registered with `GET /payments/{payment_id}` (where `payment_id: uuid.UUID`) will happily match a request for `GET /payments/webhook` first if it was registered earlier, treating `"webhook"` as the (not-yet-validated) `payment_id` — sending the request into the wrong handler entirely (this actually happened: PesaPal's webhook calls were landing in `read_payment`'s auth check and returning 403 instead of hitting `payment_webhook`). Any router with a fixed-path route that could collide with another router's `{param}` route must be registered first.
- **This dev machine tends to accumulate stale listeners on common ports** (8000, 8001, 8010 have all been seen occupied by leftover/unrelated processes from other projects) — and Windows will route a request to `localhost:<port>` to whichever process is bound to `127.0.0.1:<port>` specifically, even if a DIFFERENT, correct process is simultaneously bound to `0.0.0.0:<port>` on the same port. Symptom: the server you just started looks like it's running fine (clean startup log, no bind error) but every request returns something clearly wrong/stale/unrelated. Don't assume your own code broke - run `netstat -ano | grep :<port>` (or `Get-NetTCPConnection -LocalPort <port>` in PowerShell) and check the owning PID before debugging further. Easiest fix: just pick a different, verified-empty port for manual testing rather than fighting for a popular one.
- A custom Pydantic `field`/`AfterValidator` that raises a plain `ValueError` (e.g. `schemas.py`'s `PasswordStr`) makes Pydantic embed the actual `ValueError` **object** inside `exc.errors()`'s `ctx.error` field when FastAPI turns it into a `RequestValidationError`. `main.py`'s `validation_exception_handler` builds its own `JSONResponse` from a plain dict (for the custom error envelope), which does NOT run through FastAPI's encoder automatically the way returning a Pydantic model would - passing raw `exc.errors()` straight to `JSONResponse(content=...)` then crashes with `TypeError: Object of type ValueError is not JSON serializable`. Fixed by wrapping it in `fastapi.encoders.jsonable_encoder(exc.errors())` (the same helper FastAPI's own default handler uses internally for this exact reason). Caught by `tests/test_login_security.py`'s weak-password tests - worth remembering any time a new custom validator gets added anywhere in `schemas.py`.
- **Jinja2 (`templates/*.html`) scans the ENTIRE file for its own `{{ }}`/`{% %}` syntax, including inside HTML comments** - it has no concept of "this is just a comment, ignore it". Writing a literal curly-brace pair as plain example text in an explanatory comment (e.g. "the `{{ full_name }}` placeholder below...") breaks the template with a `TemplateSyntaxError` the moment it's rendered - this happened twice while writing `templates/password_reset.html`'s and `templates/order_confirmation.html`'s own header comments. Describe placeholder syntax in words ("a double-curly-brace placeholder") instead of typing the literal characters, anywhere inside a `templates/*.html` file.

**Established patterns to follow for new domains:**
- Soft delete (`is_active: bool`) instead of real row deletion — matches the docs, e.g. `routers/products.py`'s `DELETE` just flips the flag. Append-only audit-style tables (`RefreshToken`, `OrderStatusHistory`, `InventoryMovement`, `AuditLog`) skip `TimestampMixin` entirely and get only a manual `created_at` — they're never updated after being written, so there's no `updated_at` to track.
- Price/name fields the customer already saw get *snapshotted* onto the child row at the moment of the action (`CartItem.unit_price_snapshot`, `OrderItem.product_name_snapshot`/`unit_price`) so later edits to the source row don't retroactively change something already committed to.
- **Promotion discounts actually reduce what's charged, as of 2026-08-22 — fixed after a frontend bug report.** Before this, `CartItemRead.discounted_price` was computed correctly (`routers/cart.py`'s `_resolve_discounted_price`) but was wired up as *display-only* — `line_total`/`subtotal`/checkout/payment all still used the undiscounted `unit_price_snapshot`, so a customer could see a sale price everywhere in the UI and still get charged full price at PesaPal. Fixed in three places that all needed to agree: `schemas.py`'s `CartItemRead.line_total` now uses `discounted_price` when it's not `None`; `routers/orders.py`'s `checkout` now calls the same `_resolve_discounted_price` helper (imported from `routers/cart.py`, not duplicated — reuse matters here specifically so checkout can never drift from what the cart just showed) per line item, so `OrderItem.unit_price`/`line_total` and `Order.subtotal`/`total` all reflect the discount too. Third, related but distinct: `PaymentInitiate.amount` (a client-supplied field) was removed entirely — `routers/payments.py`'s `initiate_payment` now always charges `order.total` server-side (for PesaPal *and* cash-on-delivery), never a client-given number. That last part wasn't just about this bug — trusting a client-supplied payment amount at all was a real gap (anyone calling the API directly could have set it to anything), independent of whether the discount math upstream was correct. `tests/test_promotions.py::test_discount_actually_reduces_cart_order_and_payment_totals` drives the real cart → checkout → payment flow end-to-end to pin all three fixes together, specifically because the bug never showed up in tests that built an `Order` directly with hardcoded "correct" numbers — it only showed up going through the real price-resolution code path.
- Domain-specific business-rule errors (e.g. `InsufficientInventoryError`, `DuplicatePaymentError`, `InvalidStateTransitionError`) are plain Python exception classes registered via `@app.exception_handler(...)` in `main.py`, not raised as raw `HTTPException` inline — keeps the HTTP-status/`error_code` mapping in one place.
- Every successful response is wrapped in `{"success": true, "message": ..., "data": ...}` automatically — give a router `route_class=EnvelopeRoute` (import from `envelope.py`) at construction and every route on it gets wrapped for free, no per-route changes needed. Errors get the matching `{"success": false, "message", "error_code"}` shape via the global exception handlers in `main.py` (`HTTPException`, `RequestValidationError`, and each domain-specific exception above all have one). A 204 response is left alone (no body to wrap).
- Auth: two separate identity tables/flows, not one. `Customer` (+ `get_current_customer` in `security.py`) for storefront users; `StaffUser` (+ `require_staff_role(*roles)`, a dependency *factory*, in `security.py`) for internal/admin users. JWTs carry a `type` claim (`"customer"` vs `"staff"`) so one token type can't be used where the other is required. There is no public staff self-registration — `POST /staff` requires an existing Owner/System Administrator, and creating a `system_administrator` through the API is always rejected; the first admin only ever comes from `seed_admin.py`. New accounts (and any admin-issued temporary password from `POST /staff/{id}/reset-password`) start with `must_change_password: true` on `StaffRead` — a forced first-login password change, cleared by `PATCH /staff/me/password`; `POST /staff` also enqueues a welcome email (`jobs.py`'s `send_staff_welcome_email`) with the temporary password. Refresh tokens (`RefreshToken` model) are random strings, hashed with fast SHA-256 (`security.hash_refresh_token`) — NOT Argon2 like passwords, since they're already high-entropy secrets, not guessable human input, and get checked on every `/auth/refresh` call. They are **not rotated** on use, only revoked (`/auth/logout` revokes every active one for the caller's account — there's no per-token targeting since the docs give `/auth/logout` no request body; `PATCH /customers/me/status` self-closure does the same revocation for that one customer).
- **Customers have a second way in besides email/password: Google Sign-In** (`POST /auth/google`, not in the original API spec — see the dedicated section below). `google_auth_client.py` verifies the ID token the frontend gets from Google's own JS library, then rejoins the exact same road a normal login does: issues the same `access_token`/`refresh_token` pair via the same `_issue_refresh_token` helper `register`/`login` already use. A Google-only account gets `Customer.password_hash = NULL` — the column was already nullable for guest rows, so this needed zero migration.
- Some endpoints accept *either* a customer or any staff role ("Owning Customer or Staff" in the docs) — there's no single dependency for this in `security.py`. Each router that needs it (`routers/payments.py`, `routers/orders.py`) defines its own local actor-resolution dependency that decodes the JWT's `type` claim and returns either a `Customer` or `StaffUser`. Small duplication, favored deliberately over a shared abstraction, matching this project's "auth logic specific to a domain lives in that domain's router" convention (see also `cart.py`'s `get_current_cart`).
- **`StaffRole` is `system_administrator` / `owner` / `sales_attendant`** — `owner` was `inventory_manager` until a 2026-08-18 client-requested rename (a Postgres `ALTER TYPE ... RENAME VALUE`, so every existing row just got relabeled, no data migration needed). As of that same date, **Sales Attendant gained access to every admin section except Staff management (`routers/staff.py`) and Audit Logs (`routers/audit.py`)** — a deliberate widening away from the original spec's literal per-endpoint role table (§3.1/§3.3), driven by the frontend's new role model. In practice this meant adding `StaffRole.SALES_ATTENDANT` to the allow-list on every `require_staff_role(...)` call that used to name only `StaffRole.OWNER` (categories/products/variants/branches/homepage-sections/store-settings/promotions writes, the customer directory, inventory create/adjust, dashboard low-inventory/sales-summary) — `routers/staff.py`'s `MANAGE_STAFF_ROLES` and `routers/audit.py`'s `READ_AUDIT_ROLES` are the two deliberate holdouts, still Owner/System-Administrator-only. **System Administrator is separately a true superset role, as of 2026-08-08, by explicit product decision** (on top of, not instead of, the Sales Attendant widening) — `security.py`'s `require_staff_role()` special-cases `StaffRole.SYSTEM_ADMINISTRATOR` to always pass, regardless of which roles a route lists, centralized there so every route built with `require_staff_role(...)` picks it up automatically. The couple of endpoints that do their own role check instead of going through `require_staff_role()` (`routers/promotions.py`'s `include_inactive` banner listing, `routers/categories.py`'s equivalent for category groups, `routers/dashboard.py`'s revenue-visibility branch) had to be special-cased by hand to match — **any new manual `staff.role == ...`/`staff.role != ...` check added outside `require_staff_role()` needs the same `SYSTEM_ADMINISTRATOR` carve-out, or it'll silently exclude admin again** (dashboard revenue-visibility is the one deliberate exception left narrower than the rest — Sales Attendant still can't see revenue figures, per FR-ADMIN-003, unaffected by the RBAC widening). This does NOT change the separate, still-standing rule that `system_administrator` can't be *created* through the API (`POST /staff`, `PATCH /staff/{id}` both reject it) — only the seeded account itself is a superset admin, and only for what it's *allowed to do*, not who can mint more of them.
- **Sales Attendant lost Dashboard, Sales, Payments, and customer-deactivation access, 2026-08-30, at the client's explicit request during UAT** — a partial reversal of the 2026-08-18 widening above, scoped to exactly four things: all four of `routers/dashboard.py`'s endpoints (`VIEW_SUMMARY_ROLES` is now `(StaffRole.OWNER,)`, covering summary/recent-orders/low-inventory/sales-summary together since they're one module), `routers/payments.py`'s `mark_cash_payment_paid` (`MARK_CASH_PAID_ROLES` now `(StaffRole.OWNER,)` — this is the only staff-role-gated payments action in this project; `read_payment`/`list_order_payments` were never role-gated at all, so Sales Attendant still sees payment details, just can't mark cash orders paid anymore), and `routers/customers.py`'s `set_customer_status` (the deactivate action specifically — `list_customers`/`read_customer` directory *read* access is untouched). Everywhere else the 2026-08-18 widening still stands unchanged. - **Kampala delivery/pickup rework, shipped 2026-08-30, replacing a flat `DeliveryZone` model shipped earlier THE SAME DAY** — Nyson's frontend rebuilt the checkout fulfillment step around a real two-level Kampala hierarchy plus a separate flat list of upcountry pickup points, so the single-list `DeliveryZone` (`routers/delivery_zones.py`, `tests/test_delivery_zones.py`) was fully removed (model, table, router, tests) rather than kept alongside the replacement — same "hard removal, not deprecation" precedent as the 2026-08-20 branches removal. Three new models replace it (`routers/delivery.py`, `tests/test_delivery.py`): `DeliveryDivision` (a Kampala grouping label, e.g. "Nakawa" — no fee of its own), `DeliveryArea` (a door-to-door area WITHIN a division, e.g. "Ntinda", carrying its own `fee`), and `RegionalPickupStation` (a flat, un-nested upcountry pickup point — `major_town`/`address`/`fee`/`contact`). Public reads: `GET /delivery-divisions` (active only), `GET /delivery-areas?division_id={uuid}` (required query param, active areas for that division only), `GET /regional-pickup-stations` (active only). Admin CRUD for all three lives under `/admin/delivery-divisions`, `/admin/delivery-areas`, `/admin/regional-pickup-stations` — **Owner/System-Administrator only, not Sales Attendant**, same narrower-than-most-modules carve-out the old `DeliveryZone` admin routes already had. `Order` gained `delivery_division_id`/`delivery_area_id`/`regional_pickup_station_id` (exactly ONE of the three populated per Nyson's spec, all `None` = a Kampala pickup order), `delivery_fee` (unchanged column, still snapshotted), and three NAME SNAPSHOTS (`delivery_division_name`, `delivery_area_name`, `pickup_town`) that `routers/orders.py`'s `checkout()` resolves and stores at order time purely so `GET /orders/{id}` can echo them back without a second lookup once the underlying division/area/station is later renamed or deactivated — plus a new nullable `delivery_instructions` column, accepted by `CheckoutRequest` now even though Nyson's frontend doesn't send it yet (a documented "gap to know" in his spec). Unlike the old `DeliveryZone` flow, `checkout()` no longer overwrites `district`/`delivery_address` with a server-resolved value — Nyson's spec has the frontend compute and send both directly, so the server only re-validates `delivery_fee` against the real area/station fee (422 on drift, same "never trust a client-supplied money figure" principle as `PaymentInitiate.amount`'s removal) and rejects any combination of the three ids other than the one exact shape (both division+area together, station alone, or neither) with 422. `Order.total` is still `subtotal + delivery_fee`.
- **Order status lifecycle emails ("Out for Delivery", "Delivered") and a post-delivery experience rating, added 2026-08-30 at the client's request** — `routers/orders.py`'s `advance_order_status` previously sent no email at all on any transition; it now fires `jobs.py`'s `send_order_out_for_delivery_email`/`send_order_delivered_email` (via `BackgroundTasks`, same pattern as every other job) specifically on the transitions into `OUT_FOR_DELIVERY`/`DELIVERED`, gated on the order actually having a `guest_email` (same optional-email pattern as the checkout confirmation email). The Delivered email carries a "Rate your experience" link: `security.py`'s `create_order_rating_token`/`decode_order_rating_token` mint and verify a short, self-contained signed JWT (same reusable-JWT pattern as `create_password_reset_token`, just its own `type` claim and a 30-day expiry — `ORDER_RATING_TOKEN_EXPIRE_MINUTES`), pointing at a new `routers/order_ratings.py`: a fully public (no auth at all — the token IS the credential) `GET /public/order-ratings/{token}` prefill (always 200; `rating_status` is `eligible`/`already_rated`/`expired`/`invalid` — an invalid/expired token is a response *field*, not an HTTP error, so the frontend can render its own error state from that field) and `POST /public/order-ratings/{token}` submit (1-5 `score` required, optional 500-char `comment`, one rating per order enforced by both a pre-check and `OrderRating.order_id`'s own `unique=True` constraint, `404`/`409`/`410` for not-delivered/already-rated/expired respectively). No per-dimension scores in this version — overall experience only, per Nyson's confirmed decision. New env var `RATING_URL` (same fallback-placeholder pattern as `PASSWORD_RESET_URL`/`STAFF_DASHBOARD_URL`). `tests/test_order_status.py`'s two new tests and `tests/test_order_ratings.py` cover all of this.
- **Pickup-aware order status lifecycle + the Order Placed/Order Confirmed email split, added 2026-08-31 (Nyson's frontend handoff)** — a Kampala **store pickup** order (the "all three delivery ids `None`" path from the 2026-08-30 rework above) now skips `out_for_delivery` entirely: staff move it straight from `packed` to `delivered` ("Collected" to the customer), and `packed -> out_for_delivery` is rejected with `409` for one of these. Detected by `routers/orders.py`'s `is_kampala_store_pickup(order)`, itself built on `_resolve_fulfillment(order)` — both **derived, not stored columns**: `fulfillment_method`/`location` are a pure function of which of the three delivery-selection ids (if any) is set, so storing them too would just be one more place they could drift out of sync with the ids that actually decide checkout. `is_kampala_store_pickup` deliberately checks `fulfillment_method`/`location`/`delivery_fee` together, matching Nyson's own frontend helper exactly — never inferred from `delivery_fee == 0` alone (a legacy/edge-case delivery order could coincidentally have a zero fee too). `OrderRead` now echoes `fulfillment_method` (`"pickup"`/`"delivery"`) and `location` (`"kampala"`/`"outside_kampala"`) on every order so the frontend doesn't have to re-derive this itself. Outside-Kampala regional pickup is **unchanged** — still goes through the full five-step pipeline, per Nyson's explicit "not confirmed otherwise yet" note. On the `delivered` transition, a Kampala store pickup order now gets `jobs.py`'s new `send_order_collected_email` (pickup-worded, same rating-link pattern) instead of `send_order_delivered_email`. Separately, but shipped in the same batch because the client flagged it as a real bug: checkout's own confirmation email used to say "Order Confirmed" while staff still saw the order sitting in `pending` — a genuine lie about what had happened. `send_order_confirmation_email`/`templates/order_confirmation.html` were renamed to `send_order_placed_email`/`templates/order_placed.html` ("Order Placed", fires at checkout, unchanged trigger), and a brand new `send_order_confirmed_email`/`templates/order_confirmed.html` fires from `advance_order_status` specifically on the `pending -> confirmed` transition — the same `guest_email`-gated pattern every other order-status email already uses. No new `OrderStatus` enum value anywhere (per Nyson's explicit instruction) — `delivered` stays the one terminal status for both pickup and delivery, distinguished only by `fulfillment_method`/`location` and by which email fired. `tests/test_order_status.py` covers all of it — `order_setup` was changed to build a genuine Kampala door-to-door delivery order (a real `DeliveryDivision`/`DeliveryArea` row) specifically so the pre-existing five-step regression coverage stays meaningful now that "no delivery ids set" means something different; a new `pickup_order_setup` fixture covers the Kampala-pickup path.
- **Product lifecycle (permanent delete after 30 days), added 2026-08-30** — `Product` gained a `deactivated_at` timestamp (`DateTime(timezone=True)`, since it's compared against `datetime.now(timezone.utc)` — see the naive-vs-aware-datetime gotcha above), stamped by the existing `DELETE /products/{id}` and cleared by the existing `PATCH /products/{id}/reactivate`. A genuinely new endpoint, `DELETE /products/{id}/permanent`, does a real hard delete — 409 if the product was never deactivated, 409 if fewer than `PRODUCT_PERMANENT_DELETE_AFTER_DAYS` (30) have passed, and — the one deliberate extra safety check beyond what was asked — **409 if any `OrderItem` still references one of its variants**, since a real hard delete of `ProductVariant` would otherwise either violate `OrderItem.variant_id`'s own FK constraint or silently break historical order data; order history must always survive a permanently-deleted product, so this endpoint refuses rather than risk either. When it does proceed, it cascades in FK-safe order (`InventoryMovement` → `InventoryRecord`/`CartItem`/`VariantAttribute` → `ProductVariant` → `ProductImage`/`ProductDiscount`/`ProductHomepageSection` → `Product`), including a best-effort Cloudinary asset cleanup (same non-blocking, logged-on-failure pattern `delete_product_image` already uses). Deliberately gated **Owner-only** (not Sales Attendant, unlike the rest of this router) — a judgment call, not explicitly spec'd, made because this is the one product action with no undo at all. `tests/test_products.py`'s lifecycle tests cover all of the above.
- **Native storefront catalogue bundle endpoints, added 2026-08-30 per Nyson's request** — `GET /storefront/homepage-bundle` and `GET /storefront/catalogue-bundle` (`routers/storefront.py`) replace the frontend's own interim BFF (`buildHomepageBundle()`/`buildCatalogueBundle()`, a Vercel edge function fanning out to five-plus of our own public GETs and stitching them together client-side) with one server-side aggregated response each. Both are fully public and deliberately **not** wrapped in `EnvelopeRoute` — same reasoning `routers/payments.py`'s `webhook_router` skips it: the caller here is a CDN/browser cache reading raw JSON, and `Cache-Control: public, max-age=60, s-maxage=300` (exactly Nyson's ask) needs to be a real HTTP header, simplest to guarantee by returning a plain `JSONResponse` built with `jsonable_encoder` rather than relying on the envelope machinery. `homepage-bundle` returns `categories`/`category_groups`/`store_settings`/`homepage_sections` (enabled-only, metadata only) /`catalogue_products` (first 100 active products, for the frontend's price-filter bounds) /`section_products` (one `{section_id, products}` entry per enabled section, but only once it has **at least 4 matching products** — the same min-product threshold Nyson's own interim BFF already enforced client-side, moved server-side here). `catalogue-bundle` is the simpler pair: just `categories` + `products`. Both reuse existing private helpers across router files rather than duplicating query logic (`routers/categories.py`'s `_group_with_categories`, `routers/homepage_sections.py`'s `_resolve_products`, `routers/products.py`'s `_build_product_read`) — same cross-router-private-helper-import pattern `routers/homepage_sections.py` itself already used. `tests/test_storefront_bundle.py` covers both endpoints, including the min-product-threshold exclusion.
- **Branches and per-branch inventory were removed entirely, 2026-08-20, at the client's explicit request** — "We will not be using any branches anymore... All deliveries are made from same location... The branches don't need to keep track of their own inventory." Same category of deliberate, client-driven departure from the written spec as the two RBAC changes above. This was a hard removal, not a deactivation: the `Branch` model, `routers/branches.py` (the whole `/branches` API), `InventoryRecord.branch_id`, and `Order.fulfilling_branch_id` are all gone outright, not soft-deleted. `InventoryRecord` is now one row per variant, globally, unique on `variant_id` alone — checkout/cancel in `routers/orders.py` and the admin product form's stock endpoint in `routers/variants.py` were simplified to match (no more "find a branch with enough stock" search, no more "default branch" resolution for the branch-less quantity field — that whole mechanism is unnecessary now that there's no branch concept left at all). `docs/JN_Database_Design_Document.md`'s per-branch inventory design and `docs/JN_API_Specification.md`'s `/branches` endpoints stay frozen/unedited as historical reference, per this project's existing convention for such departures.
- **`POST /products` now creates a product AND its one default `ProductVariant` + `InventoryRecord` in a single call, 2026-08-20** — triggered by discovering that real catalog data entry had been producing duplicate-looking products (45 distinct names appearing 2-3 times each as separate `Product` rows) because creating a product and creating its variant used to be two separate staff actions. `ProductCreate` now requires `sku`/`price` (plus optional `quantity_available`, default 0) — `create_product` builds the `Product`, then the `ProductVariant`, then the `InventoryRecord` (+ an `InventoryMovement` STOCK_IN entry if starting stock is nonzero) all in one transaction; a duplicate SKU rolls back the whole thing (409), never leaving a variant-less product behind. **Editing an existing product still goes through a separate, metadata-only `ProductUpdate` schema** (no sku/price/quantity fields at all) — a product can still end up with more than one variant via `POST /products/{id}/variants` (unchanged, still the "this product genuinely needs a second, separately-stocked color/size" path), so there's no single price/sku a plain product-details edit could safely overwrite; editing a specific variant's price/sku goes through `PUT /variants/{id}` directly.
- **`ProductRead` gained `sku`/`price`/`quantity_available`, 2026-08-21** — the admin dashboard's product list/detail views were built expecting price/sku/stock directly on `GET /products`/`GET /products/{id}`, not a second `GET /variants?product_id=<id>` round-trip per row. `routers/products.py`'s `_default_variant()` picks the oldest *active* `ProductVariant` under the product (for the vast majority of products — created via the collapsed-create flow above — this is the only variant there is); `sku`/`price` come from that variant and are public, same as `VariantRead.price`. `quantity_available` follows `VariantRead.quantity_available`'s existing staff-only pattern exactly — real number for an authenticated staff caller (`read_product`/`list_products` now accept the same optional-bearer pattern `routers/variants.py` already used, via `_current_staff_or_none`), always `null` for a public/customer request, since actual stock counts are staff-only information (FR-PROD-017/018). A product with more than one variant (the genuine multi-color/size case) still only exposes its *first* variant's price/sku here — the full set remains a `GET /variants?product_id=<id>` call, unchanged. All three fields are `null` only in the edge case of a product with every variant soft-deleted.
- **Self-service profile updates exist for both identity types**: `PATCH /customers/me` (full_name/phone_number, `None` means "leave alone") and `PATCH /staff/me` (same two fields, any staff role including Sales Attendant) — but they differ on `phone_number`: the staff version distinguishes "field omitted" from "field explicitly sent as `null`" via Pydantic's `update.model_fields_set`, since the frontend needs to actually *clear* a staff member's phone number, not just leave it alone. `CustomerProfileUpdate` doesn't have this distinction (nothing has asked for customer-side clearing yet) — don't assume the two schemas behave identically just because they look alike.
- **Every external integration in this project is now genuinely real** — a milestone reached 2026-08-02, not a simplification list anymore: **PesaPal** (payments, LIVE credentials active on Render, confirmed end-to-end by the client on PesaPal's own dashboard), **Cloudinary** (`POST /products/{id}/images` does a real backend-mediated upload via `cloudinary_client.py`, storing the real `secure_url`/`public_id` Cloudinary hands back — no more client-supplied URLs), **Resend** (real email, see the dedicated section below), and **Google** (real ID-token verification for Sign-In). Each wrapper module (`pesapal_client.py`, `cloudinary_client.py`, `email_client.py`, `google_auth_client.py`) follows the exact same shape: an `is_configured()` check, one typed exception class, and plain functions the rest of the app calls without ever touching the underlying SDK/HTTP details directly.
- A router whose response format is dictated by an external caller (not our own API clients) should NOT use `route_class=EnvelopeRoute` — see `routers/payments.py`'s `webhook_router` vs `router`. Wrapping PesaPal's IPN acknowledgment in our own `{"success","message","data"}` envelope would break PesaPal's ability to parse it; it expects its own exact shape back.
- External-service calls (`pesapal_client.py`, `cloudinary_client.py`, `email_client.py`, `google_auth_client.py`) get **mocked at the test-suite boundary**, not hit live on every `pytest` run — see `tests/test_payments.py`'s `mock_pesapal`, `tests/test_catalog_extensions.py`'s `mock_cloudinary`, `tests/conftest.py`'s `mock_email`, and `tests/test_auth_tokens.py`'s `mock_google_auth` fixtures, each patching the router module that already imported the wrapper's functions directly (patch where the name is *used*, not where it's *defined* — patching the origin module doesn't affect a name some other module already imported directly). Each real integration is verified once, separately, against actual credentials (sandbox or live) — not something the automated suite depends on.
- Business-rule write actions get logged to `audit_logs` via `audit.write_audit_log(db, ...)` — called *inside* the same transaction as the actual change (before `db.commit()`), never in its own commit, so the audit entry and the change it describes can't succeed/fail independently. Currently wired into product create/update/status, inventory adjust, staff create/update, and order status advancement — not yet every mutating endpoint (categories/variants/banners/discounts/images aren't audited yet).

## How to work in this repo

This is a teaching context, not a normal "ship it" repo — the user is building this specifically to learn, and has given explicit, repeatedly-reinforced process rules:

- **Explain, don't just do.** Before writing a file/running a command, briefly say what it will do and why (the underlying concept, not just the mechanics). After, briefly explain what changed and why it matters. Keep explanations short and concrete — a couple of sentences, not an essay — but never skip the "why."
- **Gate on one file/command at a time.** Write or run exactly one coherent unit of work (one full file, or one full route/feature-sized addition, or one command) — then stop and let the user confirm before continuing. Don't chain multiple file writes or commands in a row without a checkpoint in between, even if the overall task was already agreed to.
- **Decide, don't ask.** For sequencing/pedagogy calls ("test this now vs. build the next file"), state the instructor's decision rather than presenting it as an open choice. Only ask real questions when it's a genuine product/scope decision only the user can make.
- **Comment code generously**, assuming a beginner-in-programming reader — explain what a decorator/mixin/dependency *is* and why a line exists, tutorial-style, not terse production-style. This is the one place in this codebase where the general "don't over-comment" default is intentionally inverted.

## Payments — PesaPal API 3.0 (real gateway, not simulated)

Client chose PesaPal over LivePay (LivePay had a 0/100 ScamAdviser trust score, hidden domain ownership, and IPQS phishing reports — too risky for a real payment integration; see project memory for the full comparison).

**Flow:** `POST /orders/{id}/payments` calls `pesapal_client.submit_order_request(...)`, stores PesaPal's real `order_tracking_id` as `Payment.provider_reference`, and returns a `redirect_url` — the frontend must send the customer's browser there (PesaPal's own hosted checkout page; we never build a card/mobile-money form ourselves). PesaPal's IPN then hits `GET /payments/webhook` with `OrderTrackingId`/`OrderMerchantReference`/`OrderNotificationType` query params — **deliberately without the actual payment status** (a PesaPal security measure) — so the handler calls `pesapal_client.get_transaction_status(...)` itself to find out what really happened, maps PesaPal's four statuses onto our `PaymentStatus` enum via `_map_pesapal_status` (`REVERSED` currently collapses onto `FAILED` — this project doesn't model refunds as their own state yet), and responds with PesaPal's required acknowledgment JSON (`{orderNotificationType, orderTrackingId, orderMerchantReference, status}`) — not our usual envelope, not the updated `Payment`.

**✅ Verified with a real, live, end-to-end sandbox test (2026-07-21)**, and again **✅ with a real, LIVE-money test (2026-08-02) — confirmed by the client on PesaPal's own merchant dashboard.** Real checkout, real PesaPal hosted payment page, real IPN callback, real DB update, real settlement. This is no longer "should work in theory" at any level — sandbox or live.

Two safety fixes were added specifically to close duplicate-charge/race-condition gaps before that live test, both in `routers/payments.py`:
- **`PaymentInProgressError`** (409, not in the original spec) — `initiate_payment` rejects a second payment attempt for an order while a real PesaPal checkout session from the last `PENDING_PAYMENT_WINDOW_MINUTES` (15) is still unresolved. This exists because the DB's own uniqueness (below) only stops us from *recording* two successful payments — it does nothing to stop PesaPal from actually charging a customer twice if a double-click or retried tab opened two separate real checkout sessions and the customer completed both.
- **Webhook race condition on `db.commit()`** — if two different payment attempts for the same order both get confirmed by PesaPal at nearly the same instant, the SELECT-based "already paid?" re-check can't fully close the race; the losing commit now catches the resulting `IntegrityError` (from the partial unique index below) and still acknowledges cleanly to PesaPal (`ack(200)`) instead of surfacing a raw 500.

**`_map_pesapal_status` must compare case-insensitively.** The docs' examples show `payment_status_description` values in all-caps (`"COMPLETED"`), but PesaPal's real sandbox returned Title Case (`"Completed"`) in the live test — an exact-match comparison silently mapped a genuinely successful payment to `FAILED`. Fixed with `.upper()` before comparing; don't remove it, and don't trust the docs' exact casing for any new PesaPal status field without checking a real response. `tests/test_payments.py::test_map_pesapal_status_is_case_insensitive` pins this.

**Env vars needed** (`.env`): `PESAPAL_CONSUMER_KEY`, `PESAPAL_CONSUMER_SECRET`, `PESAPAL_BASE_URL` (sandbox `https://cybqa.pesapal.com/pesapalv3` vs live `https://pay.pesapal.com/v3` — **the base URL must match which kind of credentials you have, or auth fails with a confusing `invalid_consumer_key_or_secret_provided` error that looks like a bad key/secret but isn't**), `PESAPAL_IPN_ID` (from running `register_pesapal_ipn.py` once), `PESAPAL_CALLBACK_URL` (where the customer's *browser* lands after paying — a page on the real storefront frontend, not this API; defaults to a localhost placeholder that must be replaced before going anywhere near real users).

**Two distinct credential sets exist for this project — never mix up which environment has which:**
- **LIVE** — the client's real JN Electronics PesaPal merchant account. Settlement contract is now signed and **these are the ACTIVE credentials on Render (production)** as of 2026-08-02 — real money, confirmed working end-to-end. Kept only as a *commented-out reference* in local `.env` (`LIVE_PESAPAL_CONSUMER_KEY` etc.) — never activate these locally; a local `uvicorn --reload` run must never be able to move real money by accident.
- **SANDBOX** — PesaPal's own **publicly published** shared demo/test merchant credentials (a `pesapal_sandbox_keys.json` PesaPal distributes, with one credential set per country — Kenya/Uganda/Tanzania/etc.). No signup needed, no real money, safe to commit to memory/docs (though still not to git). This project uses the **Ugandan Merchant** set (matches the target market) and is what's active in local `.env` for all local dev/testing — Render (production) does NOT use these anymore.

Each environment also needs its **own** `PESAPAL_IPN_ID` — registering a webhook URL with PesaPal is per-credential-set, not shared between sandbox and live. `register_pesapal_ipn.py` was run twice: once for the sandbox credentials (registered against the deployed Render URL, back when Render was still on sandbox), once for the live credentials (same Render URL, different registration, different resulting ID). Local `.env` keeps the sandbox IPN ID; Render's dashboard has the live one.

**Local dev needs a public tunnel** (`ngrok http <port>`) for `register_pesapal_ipn.py` and for PesaPal's IPN to actually reach this API — PesaPal is a real external service and cannot call `localhost`. ngrok's free tier now requires an account + authtoken (`ngrok config add-authtoken <token>`) even to start a tunnel. If ngrok errors with `ERR_NGROK_121` ("agent version too old"), run `ngrok update` first — the winget package installs an outdated version.

**PesaPal's access token expires every 5 minutes** — `pesapal_client.py` caches it in a module-level variable with a 30-second refresh margin rather than fetching a new one per call.

**Live for real users as of 2026-08-02.** `pesapal_client.is_configured()` returns `False` only when NEITHER key is set (i.e. `initiate_payment` degrades gracefully if `.env` ever ends up with no PesaPal credentials at all - e.g. a fresh clone before setup) — with Render now holding the live credentials, real customer payments work for real.

**Background workers — built two ways; only one is currently wired in.**

**Currently ACTIVE: FastAPI `BackgroundTasks`.** `routers/auth.py`'s `forgot_password` calls `background_tasks.add_task(send_password_reset_email, ...)` (`jobs.py`) - runs in the same process as the API, after the response is sent, no separate worker or Redis needed. Chosen for the pilot launch specifically because **Render's Background Worker service type has no free tier at all (starts at $7/month)**, while the free Web Service plan was already sufficient. Trade-off, accepted deliberately: if the web process restarts mid-task, the task is lost - acceptable for a job this low-stakes (worst case, a user re-requests a password reset); revisit if a future job actually needs to survive a restart or genuinely can't run in-process.

**Three more jobs added the same way** (all in `jobs.py`, all called via `background_tasks.add_task(...)`, never given a DB session or ORM object — only plain values, since the request's own DB session has already closed by the time a `BackgroundTasks` callback runs): `send_order_confirmation_email`/`notify_staff_new_order` (from `routers/orders.py`'s `checkout`, at order placement) and `send_payment_confirmed_email` (from `routers/payments.py`'s `payment_webhook`, only when a payment resolves to `PAID`). See "Email (Resend)" below for what each actually sends.

**Built but NOT called from anywhere: RQ + Redis + a real worker process.** `redis_queue.py` (connection + the shared `job_queue`), `worker.py` (the standalone process: `python worker.py`, runs forever pulling jobs off Redis). This is a fully working, previously-verified-live alternative - switching back means changing exactly one call site (`background_tasks.add_task(...)` → `job_queue.enqueue(...)` in `routers/auth.py`), not rebuilding anything. Worth reviving if: job volume grows enough that blocking the request thread matters, a job needs to survive a process restart, or the project reaches a point where $7/month is trivial compared to what real cross-process queueing buys.

Redis for that path runs locally via Docker: `docker run -d --name jn-redis -p 6379:6379 --restart unless-stopped redis:7-alpine`, `REDIS_URL=redis://localhost:6379` in `.env`. `--restart unless-stopped` means it survives a Docker Desktop restart automatically. (A free Render Key Value instance was also confirmed available if this path gets revived in production - only the Background Worker service type itself is the paid piece.)

**Two genuine Windows/RQ incompatibilities were hit building the RQ path - both fixed, both worth knowing before reviving `worker.py`/`jobs.py`'s RQ call site:**
- RQ's regular `Worker` class forks a child process per job (`os.fork()`) for isolation - `os.fork()` doesn't exist on Windows at all and crashes the instant a job arrives. Fixed by using `SimpleWorker` instead (runs jobs in the same process, no fork). Trade-off: a job that crashes badly enough could in theory take the whole worker down with it, not just itself - acceptable for this project's jobs.
- RQ's default job-timeout mechanism (`death_penalty_class`) relies on `signal.SIGALRM`, also Unix-only. Fixed by overriding it to `rq.timeouts.TimerDeathPenalty` (a background-thread-based timeout that works cross-platform) - it's a class attribute, not a constructor argument, so it gets set on the worker instance after construction (`worker.death_penalty_class = TimerDeathPenalty`), not passed into `SimpleWorker(...)`.

`tests/test_background_jobs.py` tests the currently-active `BackgroundTasks` path - `TestClient` runs background tasks to completion before `client.post(...)` returns, so a plain assertion after the call works, no special waiting needed.

## Google Sign-In

**`POST /auth/google`** (not in the original API spec - added afterward at the client's request) - a second way for a *customer* to authenticate, alongside email/password. `google_auth_client.py` wraps Google's ID-token verification (`google-auth` package): the frontend gets a signed ID token from Google's own JavaScript library after the customer signs in with Google, sends it to this endpoint, and `verify_id_token` confirms the signature is genuinely Google's, the token hasn't expired, and - critically - that `GOOGLE_CLIENT_ID` matches the token's own "issued for this app" claim (so a token meant for some other app can't be replayed here).

**Account-linking policy (a real product decision, not just an implementation detail):** if the verified email matches an existing password-based `Customer`, that customer is logged into their *existing* account - auto-linked, no separate "connect your account" step. This is gated on Google's own `email_verified` claim being `true` (Google only sets this once it has confirmed the person actually owns that email) - the same default Firebase/Auth0/Supabase all use, chosen over a stricter explicit-opt-in flow since it needs zero extra frontend work and isn't actually less safe (we're trusting Google's verification, not a raw string match). A brand new Google sign-in creates a `Customer` with `password_hash = NULL` - already-nullable (guest rows use it too), so no migration was needed.

Same `is_configured()`/typed-exception (`GoogleTokenError`) shape as every other wrapper module; `GoogleSignInUnavailableError` degrades to a 503 if `GOOGLE_CLIENT_ID` is ever missing, same pattern as `PaymentsUnavailableError`.

**`GOOGLE_CLIENT_ID` is the same value on three sides** - this backend (audience verification), Nyson's frontend (initializing Google's sign-in button), and the Google Cloud Console OAuth client's "Authorized JavaScript origins" list (every real frontend origin, kept in sync with `CORS_ALLOWED_ORIGINS`).

## Cloudinary (real image uploads)

**`POST/PUT /products/{id}/images` do real backend-mediated uploads** - the frontend sends the actual image file (`multipart/form-data`), this API uploads it to Cloudinary via `cloudinary_client.py` (the official SDK, not raw HTTP - Cloudinary's SDK handles the multipart upload construction, worth using here unlike PesaPal/Resend's single simple JSON calls), and stores the real `secure_url`/`public_id` Cloudinary hands back. This replaced the original simplification where a client just supplied an arbitrary already-hosted URL.

Chosen deliberately over having the frontend upload directly to Cloudinary with an unsigned preset - keeps all Cloudinary credentials server-side only, consistent with how PesaPal/Resend/Google are all backend-mediated too, not client-side.

`DELETE` and `PUT` (replace) both also call Cloudinary's `destroy` - deleting/replacing an image now actually removes the old asset from Cloudinary storage, not just the DB row. A failed cleanup delete (e.g. Cloudinary briefly unreachable) is logged as a real Sentry Issue but does NOT fail the request - the thing the client actually asked for (the replace/delete) already succeeded.

## Observability (Sentry + logging)

**Two separate PROCESSES need their own setup** — the API (`main.py`) and the worker (`worker.py`) never share a Python process, so configuring Sentry/logging only in `main.py` would leave the worker silently unmonitored. Both call `observability.setup_observability()` once at their own startup — see that file's docstring. Don't configure Sentry/logging directly in `main.py` or `worker.py` again; add to `observability.py` instead so both processes stay in sync.

**`enable_logs=True`** means Python's standard `logging` module output goes to Sentry too, not just unhandled exceptions — one dashboard for both instead of a separate logging service. Get a logger the normal way (`logger = logging.getLogger(__name__)`) and call `logger.info`/`.warning`/`.exception` — no per-file setup needed, `logging.basicConfig()` in `observability.py` already configured the root logger. Currently wired into `jobs.py` (replacing an old `print()`), `routers/orders.py`'s `checkout` (order placed / insufficient stock), and `routers/payments.py` (payment initiated, PesaPal gateway failures, webhook outcomes) — not yet every route. The two CLI scripts (`seed_admin.py`, `register_pesapal_ipn.py`) deliberately still use `print()`, not `logging` — they're one-off scripts a human runs and reads output from directly, not part of the running service.

**Log level is the signal for what becomes a Sentry Issue vs. a quiet breadcrumb.** `logger.info`/`.warning` for expected business outcomes (a declined card, insufficient stock, a stray webhook callback) — these matter for visibility but aren't bugs. `logger.exception`/`.error` for genuine infrastructure failures (PesaPal unreachable) — these SHOULD interrupt someone. Sentry's default behavior turns ERROR+ into its own Issue; INFO/WARNING become breadcrumbs attached to whatever error follows, not separate alerts. Keep using this distinction deliberately when adding new log calls — logging a normal business outcome at ERROR level would create alert fatigue.

**`send_default_pii=False`, overriding Sentry's own onboarding snippet default of `True`** — this project handles real customer PII (emails, phone numbers, delivery addresses); sending it to a third party needs to be a deliberate future decision, not the default.

**pytest runs now genuinely talk to real Sentry** (tagged `environment=development`, from `.env`) — there's no test-mode bypass. Test runs occasionally show `"Sentry is attempting to send N pending events"` in the output; that's expected, not a bug. If Sentry's dashboard ever needs to be read cleanly without test noise, filter by environment.

**Testing logger output needs `caplog`, not `capsys`.** `logging.basicConfig()` runs once at import time and binds its handler to whatever `stderr` existed then; pytest's `capsys` substitutes `sys.stdout`/`sys.stderr` per-test, which the already-bound handler doesn't see. `caplog` attaches its own handler directly to the `logging` module instead, independent of stream redirection — use it for any test asserting on log output (see `tests/test_background_jobs.py`).
