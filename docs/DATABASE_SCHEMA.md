# JN Electronics — Database Schema Reference

For the frontend team. This reflects the **actual current database schema** as implemented in `models.py` — not the original `JN_Database_Design_Document.md`, which was written before several tables existed (Payments, Promotions, Audit Logs, Refresh Tokens, Inventory Movements, Product Images, Variant Attributes, Order Status History) and predates a few structural changes (e.g. price lives on `product_variants`, not `products`).

If this ever looks out of date, `models.py` in the backend repo is the real source of truth — this file is a snapshot of it.

## How to read this doc

- **Type** is the Postgres column type. In API JSON responses, these come across as:
  - `UUID` → string, e.g. `"b1f3a2c4-..."`
  - `TIMESTAMPTZ` → ISO 8601 string, e.g. `"2026-07-21T10:30:00Z"`
  - `BOOLEAN` → `true`/`false`
  - `ENUM` → its lowercase string value (see each enum's value list below — never the Python-style name)
  - money fields (`price`, `amount`, `total`, etc.) → plain numbers, not cents/integers. **Note:** these are stored as `FLOAT`, not a fixed-precision `NUMERIC(12,2)` (a deviation from the original design doc) — do float-safe rounding/formatting on the frontend (e.g. `toFixed(2)` for display) rather than assuming exact decimal precision from the API.
- **Nullable** — whether the field can be `null` (or absent-equivalent) in a response.
- Every table has a UUID primary key column named `id`, generated by the backend (not auto-increment) — not re-listed per table below.
- Most tables have `created_at`/`updated_at` (both `TIMESTAMPTZ`, set automatically by the database). A few append-only/audit-style tables (marked below) only have `created_at` — they're written once and never edited.
- "Soft delete" tables use an `is_active` flag instead of ever actually removing a row — deactivated rows still exist, just filtered out of normal listings.

## User roles & account types

There are **two completely separate identity systems** — customers (storefront users) and staff (internal/admin users) — not one user table with roles. A customer token and a staff token are never interchangeable.

### Staff roles (`staff_role` enum)

Determines what a staff account is allowed to do. One role per staff account.

| Value | Meaning |
|---|---|
| `system_administrator` | Seeded account only (created once, outside the API, via a setup script — no one can create another through the API). Scoped to initial configuration and staff account management, **not** an implicit superset of the other two roles — e.g. it cannot view/adjust inventory, only Inventory Manager and Sales Attendant can. |
| `inventory_manager` | Full operational access — catalog, branches, inventory, staff management, promotions, dashboard, audit logs. |
| `sales_attendant` | Limited scope — can view (not manage) inventory, advance order statuses, and view the dashboard's summary/recent-orders widgets (with revenue figures hidden). Explicitly locked out of the entire staff-management module, except changing their own password. |

### Customer type (`customer_type` enum, on `customers.customer_type`)

| Value | Meaning |
|---|---|
| `guest` | Not currently created through any endpoint — reserved for future guest-account tracking. Guest checkout today doesn't create a `customers` row at all; it's identified purely by an `X-Guest-Token` header. |
| `registered` | A real account created via `/auth/register`. Default value for every row actually created today. |

### Customer status (`customer_status` enum, on `customers.status`)

| Value | Meaning |
|---|---|
| `active` | Default. Can log in. |
| `inactive` | Deactivated by an Inventory Manager — login is blocked (403) even with the correct password. |

## Catalog

### `categories`

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `name` | VARCHAR(100) | No | Unique. |
| `description` | TEXT | Yes | |
| `is_active` | BOOLEAN | No | Soft-delete flag, default `true`. |

### `products`

The shared "listing" — name and category only. Price, SKU, and stock all live on `product_variants`, not here.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `category_id` | UUID (FK → `categories.id`) | No | |
| `name` | VARCHAR(200) | No | |
| `is_active` | BOOLEAN | No | Soft-delete flag, default `true`. |

### `product_variants`

The actual purchasable/priced/stocked item under a product (e.g. a specific color/capacity combination).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `product_id` | UUID (FK → `products.id`) | No | |
| `sku` | VARCHAR(64) | No | Unique across the whole catalog. |
| `variant_label` | VARCHAR(150) | Yes | Human-readable, e.g. `"128GB / Midnight Black"`. |
| `price` | FLOAT | No | |
| `is_active` | BOOLEAN | No | Soft-delete flag, default `true`. |

### `product_images`

*No `updated_at`.* Real Cloudinary upload isn't wired up yet — `image_url` is just a URL the client already has hosted; `cloudinary_public_id` is always `null` for now.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `product_id` | UUID (FK → `products.id`) | No | |
| `image_url` | VARCHAR(500) | No | |
| `cloudinary_public_id` | VARCHAR(255) | Yes | Always `null` currently. |
| `is_primary` | BOOLEAN | No | Exactly one `true` per product, enforced by the database. Default `false`; the *first* image uploaded for a product is auto-set to `true`. |
| `display_order` | SMALLINT | No | Default `0`. |
| `created_at` | TIMESTAMPTZ | No | |

Max 5 images per product (enforced by the API, not the database).

### `variant_attributes`

*No timestamps at all.* Flexible key/value pairs per variant (e.g. `color` → `"Black"`, `capacity` → `"128GB"`) instead of fixed columns.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `variant_id` | UUID (FK → `product_variants.id`) | No | |
| `attribute_name` | VARCHAR(50) | No | e.g. `"color"`. |
| `attribute_value` | VARCHAR(150) | No | e.g. `"Black"`. |

Unique per `(variant_id, attribute_name)` — a variant can't define the same attribute twice. In API responses this comes back as a nested `attributes: { "color": "Black", "capacity": "128GB" }` object on the variant, not a flat list of rows.

## Branches & Inventory

### `branches`

Never exposed to the customer-facing storefront — staff-only visibility.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `name` | VARCHAR(150) | No | |
| `address` | VARCHAR(255) | No | |
| `phone_number` | VARCHAR(20) | Yes | |
| `email` | VARCHAR(255) | Yes | |
| `is_active` | BOOLEAN | No | Soft-delete flag, default `true`. |

### `inventory_records`

One row per (variant, branch) pair. Not soft-deletable — a zero-stock row is still meaningful.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `variant_id` | UUID (FK → `product_variants.id`) | No | |
| `branch_id` | UUID (FK → `branches.id`) | No | |
| `quantity_available` | INTEGER | No | Never negative (database-enforced). Default `0`. |
| `quantity_reserved` | INTEGER | No | Never negative (database-enforced). Default `0`. |

Unique per `(variant_id, branch_id)`.

### `inventory_movements`

*No `updated_at`.* Immutable, append-only audit trail of every stock change.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `inventory_record_id` | UUID (FK → `inventory_records.id`) | No | |
| `movement_type` | ENUM `movement_type` | No | `stock_in`, `stock_out`, `reserved`, `sold`, `adjustment`. |
| `quantity_changed` | INTEGER | No | Signed — positive = stock in, negative = stock out. |
| `reason` | VARCHAR(255) | Yes | |
| `staff_user_id` | UUID (FK → `staff_users.id`) | Yes | `null` for a system-generated `sold` movement (checkout) — no staff actor involved. |
| `order_id` | UUID (FK → `orders.id`) | Yes | Set when the movement came from an order (checkout or cancellation); `null` for a standalone manual adjustment. |
| `created_at` | TIMESTAMPTZ | No | |

## Cart

### `carts`

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `customer_id` | UUID (FK → `customers.id`) | Yes | Exactly one of `customer_id` / `guest_token` is set, never both, never neither (database-enforced). |
| `guest_token` | VARCHAR(100) | Yes | Client-generated (e.g. a UUID it makes itself) and sent as the `X-Guest-Token` header — there's no endpoint that issues one. Unique. |
| `status` | ENUM `cart_status` | No | `active`, `converted` (checked out), `abandoned`. Default `active`. |

### `cart_items`

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `cart_id` | UUID (FK → `carts.id`) | No | |
| `variant_id` | UUID (FK → `product_variants.id`) | No | |
| `quantity` | INTEGER | No | Must be `> 0` (database-enforced). |
| `unit_price_snapshot` | FLOAT | No | Captured at add-to-cart time — later price changes on the variant don't retroactively affect items already in a cart. |

Unique per `(cart_id, variant_id)` — adding the same variant again increments quantity instead of duplicating the row.

## Orders

### `orders`

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `order_number` | VARCHAR(30) | No | Human-friendly, e.g. `"JN-20260721-0001"`. Unique. The real primary key is still `id`. |
| `customer_id` | UUID (FK → `customers.id`) | Yes | `null` for a guest order. |
| `fulfilling_branch_id` | UUID (FK → `branches.id`) | Yes | `null` until checkout finds a branch with enough stock. |
| `guest_full_name` | VARCHAR(150) | No | Collected fresh at every checkout, even for a registered customer. |
| `guest_phone_number` | VARCHAR(20) | No | |
| `guest_email` | VARCHAR(255) | Yes | |
| `delivery_address` | VARCHAR(500) | No | |
| `status` | ENUM `order_status` | No | See lifecycle below. Default `pending`. |
| `requires_prepayment` | BOOLEAN | No | Currently always `false` — not yet wired to the real payment flow. |
| `subtotal` | FLOAT | No | |
| `total` | FLOAT | No | Same as `subtotal` today — no tax/delivery-fee/discount logic applied to it yet. |

**`order_status` lifecycle:**
```
pending → confirmed → packed → out_for_delivery → delivered
pending → cancelled
confirmed → cancelled
```
`delivered` and `cancelled` are terminal — no further transition is valid from either. Enforced by the API, not the database.

### `order_items`

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `order_id` | UUID (FK → `orders.id`) | No | |
| `variant_id` | UUID (FK → `product_variants.id`) | No | |
| `product_name_snapshot` | VARCHAR(200) | No | Captured at checkout — stays accurate even if the product is later renamed. |
| `variant_label_snapshot` | VARCHAR(150) | Yes | Same snapshot reasoning. |
| `quantity` | INTEGER | No | Must be `> 0` (database-enforced). |
| `unit_price` | FLOAT | No | Snapshotted price at checkout. |
| `line_total` | FLOAT | No | |

### `order_status_history`

*No `updated_at`.* Immutable log of **staff-driven** status changes only — a customer's own self-service cancel does *not* write a row here (there's no staff actor to attribute it to).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `order_id` | UUID (FK → `orders.id`) | No | |
| `from_status` | VARCHAR(30) | Yes | Plain string, not the enum type. `null` only on a (currently unused) initial-creation entry. |
| `to_status` | VARCHAR(30) | No | |
| `changed_by_staff_id` | UUID (FK → `staff_users.id`) | No | |
| `notes` | VARCHAR(500) | Yes | |
| `created_at` | TIMESTAMPTZ | No | |

## Payments

Backed by the real PesaPal API 3.0 gateway (not simulated).

### `payments`

One row per payment **attempt**, not per order — a declined card followed by a successful mobile money retry is two rows against the same order.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `order_id` | UUID (FK → `orders.id`) | No | |
| `provider` | VARCHAR(50) | No | Free-text client-supplied label, e.g. `"mobile_money"`, `"card"`, `"cash_on_delivery"` — informational only, PesaPal's own hosted page is what actually determines the payment method. |
| `status` | ENUM `payment_status` | No | `pending`, `awaiting_payment`, `paid`, `failed`. Default `pending`; set to `awaiting_payment` as soon as PesaPal accepts the order. |
| `amount` | FLOAT | No | |
| `currency` | VARCHAR(3) | No | Default `"UGX"`. |
| `provider_reference` | VARCHAR(150) | Yes | PesaPal's real `order_tracking_id` once initiated. |
| `failure_reason` | VARCHAR(255) | Yes | |
| `redirect_url` | VARCHAR(500) | Yes | PesaPal's hosted checkout page — **the frontend must redirect the customer's browser here** to actually pay. Present once `awaiting_payment`. |
| `initiated_at` | TIMESTAMPTZ | Yes | |
| `completed_at` | TIMESTAMPTZ | Yes | |

Only one `paid` payment is ever allowed per order (database-enforced) — a second attempt on an already-paid order is rejected with a `409`.

## Promotions

### `banners`

Public homepage banners. The public listing endpoint only returns rows that are both `is_active = true` **and** currently inside their `starts_at`/`ends_at` window (if set).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `title` | VARCHAR(150) | No | |
| `image_url` | VARCHAR(500) | No | |
| `display_order` | SMALLINT | No | Lower shows first. Default `0`. |
| `is_active` | BOOLEAN | No | Default `true`. |
| `starts_at` | TIMESTAMPTZ | Yes | Optional schedule window. |
| `ends_at` | TIMESTAMPTZ | Yes | |

### `product_discounts`

Its own table (not columns on `products`) so discount history is retained and future windows can be scheduled ahead of time.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `product_id` | UUID (FK → `products.id`) | No | |
| `discount_type` | ENUM `discount_type` | No | `percentage` or `fixed_amount`. |
| `discount_value` | FLOAT | No | Meaning depends on `discount_type` — e.g. `15` means "15% off" or "15 currency units off" respectively. |
| `starts_at` | TIMESTAMPTZ | Yes | |
| `ends_at` | TIMESTAMPTZ | Yes | |
| `is_active` | BOOLEAN | No | Default `true`. |

## Auth & identity

### `customers`

Both guest *and* registered customers share this table (`customer_type` tells them apart) — though in practice, only `registered` rows exist today (see "User roles" above).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `customer_type` | ENUM `customer_type` | No | Default `registered`. |
| `full_name` | VARCHAR(150) | Yes | |
| `email` | VARCHAR(255) | Yes | Unique. |
| `phone_number` | VARCHAR(20) | Yes | Unique. |
| `password_hash` | VARCHAR(255) | Yes | Never returned by any endpoint. `null` for a non-registered row. |
| `status` | ENUM `customer_status` | No | Default `active`. |

### `staff_users`

Completely separate from `customers`. No public self-registration — created only by an existing Inventory Manager/System Administrator, except the very first System Administrator (seeded once, outside the API).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `full_name` | VARCHAR(150) | No | |
| `email` | VARCHAR(255) | No | Unique. |
| `phone_number` | VARCHAR(20) | Yes | Unique. |
| `password_hash` | VARCHAR(255) | No | Never returned by any endpoint. |
| `role` | ENUM `staff_role` | No | See "User roles" above. |
| `is_active` | BOOLEAN | No | Default `true`. A deactivated staff account cannot log in. |

### `refresh_tokens`

*No `updated_at`.* Never exposed via any API response — internal to the auth flow only, listed here for completeness.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `owner_type` | ENUM `owner_type` | No | `customer` or `staff` — this table is shared by both, told apart by this column (no single foreign key is possible since it points at two different tables). |
| `owner_id` | UUID | No | Points at either `customers.id` or `staff_users.id`, depending on `owner_type`. |
| `token_hash` | VARCHAR(255) | No | The raw token is never stored — only its hash. Unique. |
| `expires_at` | TIMESTAMPTZ | No | |
| `revoked_at` | TIMESTAMPTZ | Yes | Set when `/auth/logout` is called; `null` means still active. |
| `created_at` | TIMESTAMPTZ | No | |

## Audit

### `audit_logs`

*No `updated_at`.* Write-once, never modified or deleted. Not exhaustive yet — currently only covers product, inventory, staff, and order-status writes (not every mutating endpoint).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `staff_user_id` | UUID (FK → `staff_users.id`) | No | |
| `action` | VARCHAR(100) | No | Free text, e.g. `"product.update"`, `"order.status_change"`. |
| `resource_type` | VARCHAR(100) | No | e.g. `"product"`, `"inventory_record"`. |
| `resource_id` | UUID | No | Points at whatever row `resource_type` names — no single foreign key is possible since it varies. |
| `previous_value` | JSONB | Yes | Shape varies by `resource_type` — there's no fixed schema for this field. |
| `new_value` | JSONB | Yes | Same. |
| `created_at` | TIMESTAMPTZ | No | |
